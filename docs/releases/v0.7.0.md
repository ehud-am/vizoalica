# Vizoalica v0.7.0 — Install from npm, deploy from the console, and multiple environments

**Deployment support**: no D1 schema change for an existing backend. This release is about how the
console itself is installed, deployed, and run against one or more backends; the Worker and its
database contract are unchanged. Update an existing backend from the console (see below) to pick up
this release's Worker build and version reporting.

**Compatibility**: none broken. The console's local settings move to a per-environment layout under
`~/.config/vizoalica/environments/`; a pre-0.7.0 single-connection file is left exactly as it was and
offered, once, to become the first named environment — nothing is changed on disk until you name it.

Vizoalica 0.7.0 changes how the console is installed and how it manages a backend, without changing
what it collects or reports.

**Install and run the console from npm — no source checkout.** `npm install -g vizoalica` then
`vizoalica console` now carries everything the console needs, including a pre-bundled Worker and its
migrations. Deploying a brand-new backend, and updating an existing one, both run from the installed
package: no `pnpm build`, and no repository-relative path, is ever needed at deploy time.

**Deploy and update a backend from the console itself.** An admin sees a plan before anything runs —
what will be created, or for an update, the Worker's and the schema's current and expected versions
and every pending database change — approves it, and watches ordered progress with a failed step's
resume. A first deploy shows the three generated secrets exactly once. Updating an existing backend
backs up the database first (unless every pending change is purely additive and the backup is
explicitly declined), applies pending migrations, and redeploys the Worker.

**Multiple backend environments.** One console installation can now manage several independent
backends side by side — `dev`, `stage`, and `prod`, or any names you choose — instead of exactly one.
Each environment has its own Worker, D1 database, R2 bucket, Cloudflare credential (a plain API token
or OneCLI, chosen independently per environment), administrator secret, access keys, and list of
projects and websites; environments never share data or credentials. Every resource an environment
creates is named `<environment>-something`, enforced by the console, so environments can coexist in
one Cloudflare account or spread across several. An environment switcher appears in the console once
more than one environment is saved; a website owner's or analyst's access key always fixes their one
environment, so they never see it.

## Upgrading

1. If you already run Vizoalica from a source checkout, nothing changes for you yet: `pnpm vizoalica`
   commands keep working exactly as before. To move to the npm-installed console,
   `npm install -g vizoalica` and run `vizoalica console`; it finds your existing single-backend setup
   and offers, once, to name it as your first environment. Naming it moves its address, credential,
   and role hint into the new per-environment layout; the old file is left untouched.
2. To add another environment (a second backend, or the same backend managed from a second
   installation), use the environment control in the console once it appears.
3. See the [Cloudflare backend guide](../operations/cloudflare.md) and
   [schema and version guide](../operations/schema-versions.md) for how updating a backend works from
   the console.
